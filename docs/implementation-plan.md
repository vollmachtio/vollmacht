# Execution plan

Implementation proceeds through small PRs. Tasks are sequential unless explicitly independent. Every row requires the adversarial review process in CONTRIBUTING.md. A checked task means its acceptance criteria were verified, not merely that files were created.

The [v0.1 release goals](release-v0.1.md) define the first-release scope, non-goals and evidence required before tagging. Task IDs below are planning identifiers, not GitHub PR numbers.

P03 and P04 must remain experiments until findings are incorporated in P06. Do not publish production claims based on simulated authenticators. Pin dependency and toolchain versions only after checking current maintenance and advisory information.

P07 is delivered in bounded slices. P07a adds the core structural application-JSON parser: fixed byte/depth ceilings, decoded duplicate rejection, printable ASCII and restricted integer syntax. Its immutable output is not a validated mandate, and it does not handle signed WebAuthn client data. P07b adds the exact approval payload schema, its original/canonical byte caps, branch grammar and canonical-input equality, tested against the independent current-profile approval bytes. P07c adds canonical envelope structure and mandate/operation/envelope digests against independent vectors; retained evidence stays opaque and unverified. P07d adds exact canonical execution and enrollment-possession payload schemas; their signatures, trusted pending-context bindings and freshness remain unchecked. P07e adds the exact public P-256 JWK and canonical enrollment-proposal schemas, maintained-library point validation, RFC 7638 thumbprints and the administrative authorization digest. Key validity and digest binding do not establish possession or enrollment. JOSE, WebAuthn verification and current-state authorization keep their separate gates. These slices alone supply no authorization. Core measurement remains explicitly unmeasured until coverage collection is integrated; passing parser tests is not a coverage-regression guarantee.

P08a adds strict compact-JWS preflight for the caller-selected issuer, execution or enrollment-possession role: bounded canonical segments, exact deterministic headers, role-specific payload schemas and preserved original signing input. Its result is explicitly unverified. P08b adds explicit one-time verification-provider startup and ES256 signature checking against a caller-supplied key binding, after strict preflight. Agent-role bindings recompute the key thumbprint; successful signature checking alone does not establish trusted registry resolution, WebAuthn evidence, current state or authorization. P08c adds immutable typed signing-input preparation, exact callback-input guards and final-output validation against the same bytes and public key. It exposes no signer or authority. Production encoder/provider integration, private one-use handle binding and coordinator deadlines remain later P08 work; unsupported signing/provider operations still fail without fallback.

P09a adds the separate signed-client-data syntax boundary: immutable original bytes, bounded UTF-8 JSON, decoded duplicate rejection and the accepted Unicode/extension policy. It performs no WebAuthn semantic or signature verification. P09b enforces that syntax policy inside the experimental version 1 Node assertion helper before security-field decoding, using a pinned maintained visitor and shared ambiguity vectors. This does not promote the experimental helper into a production service. Registration integration, production Rust ingestion, packaging, enrollment, registry state and evidence rechecking remain subsequent P09 work.

P03 is split for review: P03a adds an executable library compatibility probe and dependency checks; P03b adds the local browser ceremony and physical testing. P03a does not complete P03. Custom mandate-challenge support is a separate gate from successful random-challenge authentication. See [probe findings](../spikes/webauthn/README.md).

P03c establishes synthetic custom-challenge feasibility with SimpleWebAuthn in an isolated Node experiment. P03d adds its opt-in [real-browser assessment](../spikes/simplewebauthn/BROWSER.md). The user-reported Chrome/Safari functional matrix, including replay rejection, is complete; historical environment versions and cleanup were confirmed on 2026-09-29. Observation limits remain documented. Neither step selects a production Node helper or resolves P04b protected key storage. The [helper assessment](helper-assessment.md) defines proposed P03e protocol and P03f packaging spikes before the P06 decision.

P04 is also split: P04a tests a temporary Secure Enclave key, independent signature verification and encoding; P04b evaluates durable protected storage, signed identity/entitlements, restart and denied-access behavior. Ephemeral signing alone does not complete P04. See the [Apple key experiment](../spikes/macos-key/README.md). It can proceed independently while P03b physical browser evidence is collected.

## Outcome-based milestones

P06a and P06b split the existing P06 task. The [P06a acceptance record](architecture/portable-acceptance.md) defines the portable freeze, effective only after its independently reviewed change merges with required checks. P06b remains unaccepted. P06a specifies security requirements and failure behavior at every deferred provider boundary, including trusted enrollment, bootstrap reconciliation and issuer provenance. If an unresolved deployment choice changes those semantics, that affected interface remains blocked until reviewed and frozen. A test-only provider must be isolated from live configuration and cannot become a default or fallback. This split permits portable implementation after P06a acceptance; it does not waive P04b or qualify a deployment.

P06b specifies and validates the concrete authority boundary: agent location and access, executor ownership, protected bootstrap anchor, registry/replay state, runtime integrity, issuer provider and GitHub credential. The maintainer approved the design direction of an isolated agent VM with the trusted executor and approval UI on the Mac. This is not setup authorization or deployment qualification: VM product, configuration, transport and shared-resource restrictions still require review. No account, signing configuration or weaker key-storage fallback is selected here. Required physical evidence remains a gate for the corresponding live deployment and release claims. A screen-lock observation alone does not establish Keychain-lock behavior.

Tasks spanning milestones are delivered in separate coherent slices; their full acceptance is not claimed from the first slice. For example, P21 audit work does not qualify credential storage, and P23 simulation does not complete a physical live demo. Use the original task ID plus a descriptive slice in each PR.

Advanced rotation/recovery, MCP, GitHub App credentials, additional platforms, external verifiers, multi-hop delegation and other write actions follow later. Credential disable, safe failure/recovery semantics and replay protection are not deferred. Standards mappings document gaps; transport adapters are separate follow-up work.

### Next execution queue

Reprioritized 2026-11-03: delivery is measured by a runnable workflow, not additional isolated components. P06a and P07 are already accepted/delivered; do not repeat their research. This changes execution order and scope priorities, not the frozen security contract or live deployment gates.

1. Finish review and delivery of the already implemented signing-input guards. Then integrate existing components into one executable, automated simulated merge flow: proposal, approval evidence, mandate, agent proof, verification and exactly one simulated action. Label test credentials/providers explicitly and prevent their reaching any live adapter. Include rejection of changed operation, invalid evidence, expired approval and replay. This is an integration checkpoint, not the live MVP.
2. Close the same flow's real approval and durable-state gaps. Integrate the selected WebAuthn helper, minimal trusted enrollment/disable, transactional replay state, restart/crash behavior and fail-closed execution. Keep one principal, one agent, one repository and one merge operation; implement required contract semantics without adding generic configuration or extension frameworks.
3. In parallel, prepare the exact P06b qualification checklist and native test instructions for the isolated-agent-VM/Mac-executor boundary. Request manual support as soon as a concrete test is ready. Do not configure the environment or perform hardware work without scoped authorization.
4. Enable the constrained disposable-repository live flow only after deployment qualification and the durable-state checks pass. Demonstrate physical approval of the exact merge, successful execution, then replay rejection. Preserve the approved head-SHA check and documented no-retarget constraint. This completes the working MVP.
5. Only then prioritize experimental release packaging, polished Pages, recordings and broader developer onboarding. Until then, maintain only the accurate runnable instructions and security limitations needed for the current flow.

No new standalone research, general-purpose abstraction, optional diagnostic, additional platform/action, or standards refresh enters the MVP critical path unless it resolves a demonstrated integration or security blocker. Existing mandatory CI, adversarial review, tests and coverage policy remain unchanged. Necessary security fixes take priority over this scope freeze.

The first integration checkpoint is the [simulated merge test](development.md#integrated-simulated-merge): fixed signed artifacts traverse the actual core signature verifier and Node WebAuthn helper before reaching a recording-only adapter. It covers verification and in-memory consumption, not the complete milestone B. Fresh proposal/approval/issuance, trusted enrollment, durable state and a user-facing command remain unfinished; do not count this fixture-based test as a working product or live MVP.

P10's portable verification slice moves signature, retained-record, evidence-context, digest, profile, audience and time checks into core. Its result is a verification candidate, never a dispatch permit. Trusted context must come from the coordinator's authenticated state, and its evidence adapter remains a trusted implementation boundary. The coordinator must claim a matching attempt before verification, consume failures, recheck current revisions/status/session/deadlines and reserve atomically before dispatch. These store duties are not implemented by immutable context objects. The simulation exercises this shared verification path with its explicitly fake store; real issuance, enrollment and durable enforcement remain next integration work.

The fresh synthetic-flow test adds newly generated proposals, synthetic assertions and signed mandate/proof artifacts to that integration, using existing core guards and the real WebAuthn helper. Test-only software keys and in-memory state cannot reach live adapters. This removes reliance on pre-signed artifacts for one test path, but does not complete production issuance, protected enrollment or milestone B's user-facing workflow. Keep the fixed-vector tests alongside it; move next to the real coordinator and durable state rather than adding more standalone simulation variants.

Organize parallel work around the integrated flow: one integration owner, one disjoint implementation lane for its next missing dependency, and independent adversarial validation. Prefer coherent reviewable feature slices over one PR per helper function. Every implementation PR must identify the runnable acceptance test it enables or the specific blocker it removes. Re-estimate remaining work after the first integrated run; do not promise dates from PR counts.

P11's first durable slice adds an existing-database attempt ledger with atomic matching claim, append-only rejection/audit and read-only reconciliation. Race and commit-failure tests exercise real SQLite transactions. It is not yet integrated with the simulated flow and supplies no reservation or dispatch authority. Next, connect durable claims and failure consumption to verification, then implement the frozen final reservation/disable serialization and startup invalidation requirements. Protected provisioning, trusted time, executor leasing and deployment qualification remain explicit prerequisites, not capabilities inferred from this library.

## Per-PR execution contract

Before editing, inspect the base revision, local instructions, and unrelated changes. Implement only the selected task. Run checks proportional to the change and capture commands/results. Request a separate adversarial review, fix findings, and obtain review of substantive fixes. Commit the reviewed state, push its branch, and open a PR with the review and validation evidence. The maintainer now authorizes automatic merging of in-plan PRs after independent review and required CI pass on the exact head revision. Pause for clarification, material deviations, permission blockers or user-assisted hardware steps; never bypass branch protections.

Independent workstreams may execute in parallel with disjoint file ownership and coordinated integration. P05, P06a preparation and P04b/P06b qualification work can proceed together. Proposed documents are not a frozen specification: P07 waits for P06a acceptance, and live execution waits for P06b qualification. CI must pass on the exact integrated PR head; retain existing tests and coverage policy, and never count collection alone as trusted-base coverage enforcement.

If GitHub authentication prevents PR creation, preserve the completed local branch and report the exact missing prerequisite. Never claim a PR exists until GitHub returns its URL. Dependent work can use explicitly stacked branches; PR descriptions must name their base and dependencies. Independent tasks can branch from the latest agreed foundation.

Critical path: A/P06a, B, C, D, E. P04b/P06b is a parallel path that must join before D, not a substitute for portable contract review. P32/P33 testing accompanies implementation rather than waiting for final hardening; P35 reviews the integrated release. Site polish follows stable command names and a working demo. Re-estimate delivery after A and the first integrated slice, not from PR count or coverage percentage.
