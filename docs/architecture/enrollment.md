# Candidate trusted enrollment and recovery

Status: **PROPOSED**, 2026-10-01. Companion to the [architecture proposal](README.md) and [mandate contract](mandate-contract.md), not an implemented administration API or a frozen wire format. This addresses the enrollment gate; native storage protection, signing identity and recovery evidence remain open. No existing experiment credential becomes production enrollment automatically.

## Authority before the first credential

First enrollment cannot authenticate itself with a credential that does not yet exist. Its root is deliberate operator control of the local administrator session, trusted executable/configuration and protected storage. Passkey registration alone is not authority to become administrator. V0 proposes one local principal and one active passkey; additional principals and multi-administrator policies are deferred.

An explicit local initialization command, never available through agent tools, exclusively claims a bootstrap session without holding a database transaction across browser or hardware calls. It refuses an existing initialized installation or incomplete/missing state from a previously initialized installation. Distinguishing fresh setup from a deleted database requires an independently protected installation anchor; its storage and crash reconciliation are acceptance gates, not something an empty directory proves. Generate installation, issuer, executor and principal IDs plus a random 32-byte WebAuthn user handle; display installation identity in the trusted terminal. P04b supplies the separately pinned issuer key. Partial key/database creation remains a blocked setup requiring scoped recovery, not permission to generate replacement identities silently.

Generate a one-use 256-bit administration capability, displayed only in that operator-controlled terminal and held in memory. Never put it in process arguments, environment variables, URLs, persistent browser storage, logs or agent-visible tool output. The browser receives it by deliberate paste. Hash the capability for server-side matching; comparisons are constant-time. Its lifetime is 120 monotonic seconds from capability creation, tied to the process session and one named operation: `bootstrap`, `replace_credential`, `enroll_agent` or `disable_identity`. The first authorized start irreversibly claims it for one operation ID: it cannot start another operation, but it authenticates the ordered stages of that same operation until terminal completion. Stage success never renews the capability or original deadline. It is not a bearer credential for merging PRs. Commit, cancellation, expiry, restart or terminal verification failure consumes it. An incorrect token must not invalidate another session's capability.

The executable must not infer trusted administration merely from a TTY or matching Unix user. If an agent can read the terminal, inspect the administrator process, change the registry or invoke the same trusted administration path, this boundary fails. The initial developer deployment excludes that capability; enforceable process/storage separation and signed distribution are acceptance/release gates. Do not claim a pasted localhost token provides isolation from same-user malware. No unattended default bootstrap or remotely callable reset endpoint.

## Local transport and pending state

Rust owns HTTP, capability checking and pending state; the Node helper has only a bounded registration/assertion request over private pipes. Use the existing experiment's IPv4-loopback listener and exact `http://localhost:8374` origin, `localhost:8374` Host and `localhost` RP ID. A busy port fails; never adopt an existing listener or choose another origin silently. Require same-origin Fetch Metadata, JSON content type and exactly one authorization/Origin/Host/security header. Deny CORS, preflight, query-string API variants and frame embedding. Static assets use restrictive CSP, no-store and no-referrer. No remote assets or agent-authored HTML.

Carry forward 64-KiB body, 8-KiB header, five-second request and bounded-connection limits, plus one in-flight administrative ceremony. Every command must pass a strict duplicate/unknown-field decoder, independent of HTTP framing. This is separate from canonical mandate serialization. Preserve raw signed client data; do not apply the application object's ASCII profile inside it. The experiment's exact-JSON.stringify transport is evidence, not a required production API design.

A pending administrative record contains exactly these logical fields: session ID, operation ID, operation kind, capability hash, installation ID, principal ID, user handle, immutable candidate key/credential reference if known, trusted RP/origin, registry revision snapshot, original monotonic deadline, operation phase and active stage. An active stage contains its kind, fresh ceremony ID, fresh challenge and stage phase. These are local fields, not browser-controlled claims. Stage-specific fields have typed variants, not arbitrary optional JSON. Store public candidate evidence separately with bounded sizes; no private keys.

Operation phase progresses once from `pending` to `active` to `committed` or `consumed`. Bootstrap stages are `registration → candidate_activation`; replacement stages are `registration → candidate_activation → old_credential_authorization`. Each stage moves once from `pending` to `verifying` to `completed`; only successful verification may allocate the next stage, with a new random ceremony ID and independent challenge. That transition does not complete the operation or permit another start. All stages and final commit share the original 120-second deadline with no refresh or retry of a failed stage. The last completed stage permits the atomic registry commit, not an intermediate enrollment.

Atomically claim a matching stage finish before helper work; a second finish cannot invoke another helper. Scope cancellation to the operation and current stage ID. Stale IDs cannot cancel or advance current state. Recheck deadline, capability scope and registry revision after helper completion and at commit. Cancellation, expiry, restart, invalid matching evidence or helper failure consumes the whole operation and clears the pending candidate and all stage challenges; a late helper success cannot revive it. For replacement, the old credential remains enabled unless final commit succeeds. Clearing a local candidate does not delete a passkey already created in the provider; report that narrowly scoped manual cleanup may be needed. A new attempt needs a new operator-created capability and fresh stages.

## Register and activate a passkey

1. After authorized bootstrap or replacement start, Rust fixes principal/user handle and creates an independent random 32-byte registration challenge. It is not a mandate hash. Bind it in pending state to `webauthn.create`, session, operation, origin/RP, principal and revision. Never accept a challenge, user ID or algorithm selected by the browser/agent as trusted input.
2. Generate creation options with ES256 only, `attestation: none`, `userVerification: required`, platform attachment and resident-key preference. Username/display labels identify the local installation without claiming real-world identity. Include existing credential IDs in `excludeCredentials`, but enforce uniqueness on the server too. Library-generated options must contain the exact trusted challenge and user handle; reject substitution.
3. Bound and validate the browser envelope and raw byte fields. Invoke full library registration verification with exact challenge/origin/RP, expected `webauthn.create`, UP and UV required, ES256 only. Reject `crossOrigin` other than absent/false and any `topOrigin`. Require browser id/rawId equality and equality with the credential ID extracted from authenticator data, not just agreement between two browser fields. Validate decoded COSE key as P-256 EC2/ES256 with valid coordinates; retain raw public-key bytes and initial counter/backup flags from verified authenticator data.
4. A verified registration produces a *candidate*, not an enabled credential. Request a fresh assertion with only that candidate ID in `allowCredentials`, exact user handle when returned, UV required and the same strict origin/RP checks. Its random challenge is independently generated and bound in pending state to candidate ID/public-key digest, installation, principal and `activate_credential`. This demonstrates usable private-key possession even when registration supplied none attestation; it does not establish authenticator provenance. This proposal intentionally adds an enrollment-only confirmation prompt, not a second prompt for every mandate.
5. Bootstrap commits the candidate only after its activation assertion passes. For replacement, the old credential must additionally authorize the exact candidate as described below. Until final commit, the candidate cannot issue mandates, authorize administration or replace a registry row.

With none attestation, do not infer Apple hardware, Touch ID, unique device or trusted software authenticator from successful registration. Platform attachment is a requested authenticator selection, not proof of manufacture. Synced passkeys remain permitted; UV is not universal proof of humanity. The added assertion establishes possession within this trusted session, not an authenticated civil identity. WebAuthn's [registration verification procedure](https://www.w3.org/TR/2026/REC-webauthn-3-20260825/#sctn-registering-a-new-credential) defines the underlying ceremony; this local administrative policy is Vollmacht's proposal.

## Atomic registry provenance

Only the Rust administration service writes enrollment. Persist a unique credential ID, principal/user-handle association, original COSE public key, RP/origin, counter, backup eligibility/status, enabled state, record revision and provenance reference. Provenance records the installation, scoped operation, administrator authorization reference, ceremony IDs, verification profile and commit time. It records why the local service accepted a key, not a self-authenticating trust certificate. Never enroll an arbitrary helper response absent its matching authorized pending state.

Use a serialized SQLite transaction to require the expected installation/registry revision and ceremony phase, ensure credential-ID uniqueness across enabled and disabled records, and atomically enable the new credential, disable the old one if replacing, increment revisions and consume administration authorization. Duplicate IDs reject, never upsert or relink to another principal. Revalidate all relevant status snapshots after asynchronous verification. Concurrent bootstrap/replacement has exactly one winner. Commit failure means no reported success; uncertain commit requires read-only reconciliation, never another insertion based on the same response.

Persist activation's resulting counter, not just registration's initial value. A replacement authorization updates the old credential's counter and status in the same transaction. Later mandate issuance performs its own serialized counter/revision update. Do not overwrite a newer counter with a stale helper result or assume all authenticators increment counters. Invalid backup flags or changed backup eligibility reject; backup state can legitimately change according to verified library output. Counter behavior is not durable replay protection.

Database ownership/permissions, trusted paths, no symlink redirection and executor-only writes are required but do not protect against a process with equivalent effective access. P04b protects issuer-key use, not arbitrary SQLite rows. The storage design must specify how enrollment integrity survives local tampering and restart before any stronger claim is accepted. Raw enrollment evidence is sensitive and belongs only in a protected evidence store with explicit retention/export, never routine audit logs. Hash-chained local audit is not anti-rollback storage.

## Replacement, agent keys and recovery

Replacement requires both a scoped local administration capability and a fresh assertion by the currently enabled credential. Register and activate the candidate first, then show the current and candidate credential/public-key fingerprints in a fixed template. Bind the old credential's approval challenge to the exact pending candidate, principal, operation, registry revision and fresh randomness. The binding must use a reviewed canonical, domain-separated administrative profile before implementation; it is not the merge-only Human Mandate action. Do not reuse a generic login assertion or approval of an empty candidate. Any candidate mutation requires a new authorization. Keep the old credential enabled until atomic replacement commits; cancellation cannot disable it.

Agent enrollment similarly needs scoped local administration plus current-passkey approval of the exact proposed agent public-key thumbprint. Validate the P-256 public key and require an ES256 proof of possession over a fresh installation/operation/key-bound challenge before enabling it. The agent may submit a candidate public key and possession proof but cannot grant itself trust. Define the separate administrative JWS type and vectors in P06; execution-proof and enrollment-proof types must not be interchangeable. Rotation disables the old agent key and invalidates its unreserved mandates in the same transaction. No automatic key discovery from requests or third-party attestations.

The [candidate agent-enrollment proof profile](agent-enrollment-profile.md) proposes exact new-agent fields, binding and stage ordering for that P06 review. It remains unfrozen and does not define rotation or credential replacement.

Credential/agent disabling increments status revisions and invalidates unreserved approvals through current-state checks. Preserve the baseline reservation cutoff: a reservation committed first may already execute; disabling cannot recall it. A scoped trusted local emergency-disable command may narrow authority without a working passkey, but must not enroll replacement keys, widen policy or erase consumed records. This is an availability-sensitive administrative path, not an agent endpoint.

If the only passkey is lost, v0 provides no silent recovery, reusable recovery bearer token or issuer-only bypass. Freeze new approvals and retain registry/replay/audit data. A separately authorized reinitialization procedure would need fresh installation/issuer/executor identities, explicit revocation of old access and preserved consumed-state history; it is not implemented by deleting the database or rerunning bootstrap. Restoring a backup cannot resurrect consumed authority. Account recovery, migration and lost-key reset require a separately reviewed procedure and user decision before implementation.

## Tests and remaining decisions

Automated acceptance must cover capability theft from the wrong API scope, expired/replayed/mismatched registration and activation challenges, cross-origin registration, missing UP/UV, unsupported COSE keys, ID disagreement, duplicate/reassigned credential IDs, candidate mutation after old-key approval, missing possession proof, helper success after cancellation, concurrent enrollment/replacement, stale counter/revision, locked/unavailable storage, transaction failure and restart at every phase. Confirm no secret in logs/URLs/argv and no agent endpoint can create administrative capabilities. Physical Safari/Chrome tests must exercise enrollment confirmation, replacement cancellation and timeout; earlier experiment runs do not cover this new flow.

Before acceptance: review the extra enrollment-only assertion UX; freeze administrative challenge/proof fields and vectors; assess selected-library ambiguity handling; settle protected first-admin access and registry-integrity boundaries; complete P04b evidence. If the intended agent environment shares terminal/process/registry access with the administrator, user direction is required on isolation rather than claiming tokens solve it. No account purchase, entitlement modification, hardware action or recovery reset is authorized by this proposal.

Sources consulted 2026-10-01: the W3C registration procedure above and [SimpleWebAuthn server documentation](https://simplewebauthn.dev/docs/packages/server), plus installed `@simplewebauthn/server` 14.0.2 registration verification and the repository's [browser experiment](../../spikes/simplewebauthn/BROWSER.md). Public library APIs accept explicit registration challenge/origin/RP expectations and produce credential/counter data; this proposal adds local authority, activation and transactional checks. No general WebAuthn conformance or hardware guarantee is claimed.
