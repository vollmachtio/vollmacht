# Provisional agent execution-proof vector

Assessment only, 2026-10-03. `fixtures/candidate-agent-vector.json` links a software-generated ES256 execution proof to the existing reviewed payload and envelope. It does not freeze the [candidate contract](../../docs/architecture/mandate-contract.md), implement P10, enroll an agent, reserve an operation or establish production authorization.

The agent is the standard P-256 generator point already identified by the payload's `agent_jkt`. Its private scalar **1 is intentionally public test material**, not a secret. `agent-vector-generator.mjs` constructs that private test key only in generation memory; the committed JSON contains public JWKs and signed artifacts, not a private JWK. Anyone can sign as this fixture agent. Never install or trust it operationally. The wrong-agent public key is a separate synthetic key.

The separately recorded trusted pending context contains the original mandate, operation and envelope digests, matching executor audience, a fixed 32-byte `0c` challenge and a 30-second interval inside the mandate's 120-second lifetime. Digests in the execution payload use canonical unpadded base64url, not the hexadecimal display form in earlier fixtures. Timestamps are fixed examples, not currently valid approvals. This JSON file is fixture provenance, not an authenticated registry or protected pending store.

The protected header is ES256 with candidate type `vollmacht-execution+jws` and `kid` equal to the enrolled-key thumbprint candidate. The payload contains version 1 plus exactly the pending fields. Canonical header/payload strings represent their exact UTF-8 bytes; surrounding fixture indentation is not signed. ES256 signatures cover the original compact JWS signing input and use 64-byte P1363 encoding through Node's maintained crypto API.

Three additional proofs each change exactly one field: audience, challenge or envelope digest. All three have valid signatures from the same fixture agent. They demonstrate why a valid signature is insufficient: their claims disagree with the separately recorded pending context. They are not examples of an implemented context validator rejecting requests. No time-policy function, nonce consumption, revocation check or production header validator is introduced.

Generate a replacement vector by running `spikes/simplewebauthn/agent-vector-generator.mjs` with pinned Node 24.21.0 and no arguments. It emits JSON to stdout only, validates the existing canonical bytes/digest expectations, and uses a restricted ASCII/integer/object oracle rather than a general-purpose canonicalizer. A rerun produces different signatures and a different wrong-agent key; verify and review replacements rather than expecting byte-identical random ECDSA output. Root-relative source files are resolved through the generator's own location.

Independent Rust tests must check canonical byte agreement, digest links, RFC 7638 thumbprint agreement, correct-key verification, wrong-key/tamper rejection and validly signed variant mismatches. Full runtime validation, future-issued/expired proof handling, monotonic time, durable replay protection and signed native storage remain separate gates. Production P06 acceptance is unchanged.
