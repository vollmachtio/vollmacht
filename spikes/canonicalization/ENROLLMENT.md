# Provisional new-agent enrollment vectors

Assessment only, 2026-10-06. These synthetic fixtures exercise the [proposed administrative profile](../../docs/architecture/agent-enrollment-profile.md). They do not freeze P06, implement enrollment or establish a complete enrollment proof chain. There is deliberately **no signed WebAuthn authorization linkage** in this slice. A matching digest is not administrator approval.

`fixtures/candidate-enrollment-vector.json` records exact canonical proposal A, possession payload B and protected header strings, the administrative domain bytes including one terminating zero byte, SHA-256 digest in hex/base64url, and a compact ES256 possession proof. A uses fixed synthetic IDs, revisions and nonce. B has a distinct stage ID and challenge, with a 30-second interval inside A's 120-second interval. These are fixed synthetic examples, not currently valid approvals or fresh challenges. No actual capability or monotonic deadline exists in the fixture.

The candidate is the public P-256 generator-point key already used by the execution fixture. Its private scalar **1 is intentionally public test material**, reconstructed only in generator memory. Anyone can sign these proofs; never enroll this key operationally. The fixture contains only public keys and artifacts. Reusing this known key allows a real existing execution-proof substitution control, not a claim that an enrolled execution key may be enrolled again. The `trusted` fixture section represents separately expected test inputs, not authenticated storage or an implemented pending registry.

The generator uses Node's maintained crypto APIs and a restricted ASCII/unsigned-integer/object canonical-byte oracle. Run `spikes/simplewebauthn/enrollment-vector-generator.mjs` with pinned Node 24.21.0 and no arguments. It reads the existing agent fixture and emits JSON to stdout only. ECDSA signatures vary between runs; compare canonical bytes, digests and signature validity, not whole-file equality. No additional hash is applied before the JOSE signing input.

Independent Rust JCS/OpenSSL tests compare literal bytes, domain and digest, public-key thumbprint, exact field sets, stage/time relationships and every proposal scalar leaf's digest sensitivity. Some leaf mutations intentionally violate the proposed profile; this is not parser validation or proof that an administrator rejected them. JOSE tests independently verify Node signatures, reject wrong keys and unsigned header/payload/signature changes, and demonstrate five correctly signed mismatches: audience, stage, authorization digest, candidate thumbprint and execution type. The existing execution proof also verifies cryptographically but differs from the required enrollment type and expected payload. These are explicit test comparisons, not a deployed context validator; library signature success alone does not enforce type or local authority.

Run both isolated crates' tests through the repository's existing canonicalization and JOSE checks. No dependency or runtime integration changes are required. The existing source inventory and check integration must account for these new generator/test files when this assessment lands.

Remaining work includes signed passkey evidence over A's digest, registration/bootstrap and protected installation-anchor design, strict untrusted parsing, stage consumption, original capability deadlines, cancellation/late responses, current status/revision rechecks, atomic commit and recovery. Native issuer storage, physical enrollment UX and all P04b/P06 acceptance gates remain open. Nothing here grants a GitHub capability or demonstrates user verification.
