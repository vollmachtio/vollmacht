# Apple issuer-key experiment (P04a)

P04b now includes a [portable durable-key lifecycle contract](DURABLE.md) and deterministic fake-backend tests. It has no native persistence backend and does not change the CLI below.

This isolated experiment requests a temporary Secure Enclave P-256 key through maintained Rust bindings, signs one fixed test message, and verifies the signature independently using OpenSSL. It is not a Human Mandate signer or a production key provider. It has no input signing API, listener, persistence, credential lookup, or software fallback. The main CLI remains unchanged.

## Run

From the repository root:

```sh
cargo build -p vollmacht-macos-key-probe
target/debug/vollmacht-macos-key-probe help
target/debug/vollmacht-macos-key-probe secure-enclave
```

The default command only prints help. The explicit secure-enclave command requests a new temporary key and signs a fixed domain-separated test message. It prints no key or signature bytes. Errors identify the stage; Apple creation/signing failures include only the numeric OS code, not raw error descriptions. Unsupported platforms fail without fallback. Hardware access is not invoked by CI or ordinary tests.

No permanent Keychain item is requested, so the probe provides no deletion command and never searches for or changes existing keys. Dropping the handle ends this process's access; this is not a claim about physical erasure timing inside Apple's hardware. If a future experiment needs persistent keys, it must use its own explicit identity and narrowly scoped cleanup.

## API and trust boundary

The security-framework 3.7.0 safe wrapper exposes the required options. A Swift helper or workspace unsafe-code exception is not needed for this first experiment. The workspace's unsafe prohibition does not extend into dependencies: security-framework, security-framework-sys, core-foundation and OpenSSL include native/FFI boundaries.

Configuration is explicit: EC P-256, SecureEnclave token, AccessibleWhenUnlockedThisDeviceOnly, and PrivateKeyUsage. Location is omitted; source inspection confirms the wrapper sets isPermanent=false for public and private attributes in this case. No weaker configuration is retried on failure. Default features are disabled for both Apple binding crates; security-framework-sys is used directly only for the maintained PrivateKeyUsage constant, not an unsafe call.

No user-presence or biometric access-control flag is requested. This experiment evaluates issuer-key confinement, not human authorization. In the proposed design WebAuthn supplies the human authorization evidence; adding another issuer-key biometric prompt is a separate policy decision. Do not infer that possession of a signing handle makes an agent authorized. A compromised authorized process can misuse a key even if it cannot export it.

After creation, the probe checks that private external representation is unavailable. This combines the explicit SecureEnclave creation request with a negative export check; it is local API evidence, not remote hardware attestation. The wrapper collapses export errors into absence, so absence alone cannot identify why export failed or prove device identity. Public SEC1 bytes are imported as P-256 and validated by OpenSSL.

Apple's ECDSASignatureMessageX962SHA256 hashes the message before signing. Verification independently hashes the same original bytes once. Apple's DER signature is parsed by OpenSSL and round-tripped to reject trailing/noncanonical encoding. The probe converts to 64-byte P1363 r || s and back using maintained integer/DER routines, verifies again, and requires an altered message to fail. This investigates the encoding required by ES256; it does not implement JWS. Converters check encoding shape, sign and nonzero integers; full scalar/curve validity is the verifier's responsibility. No low-S policy or signature-byte uniqueness is asserted.

## Validation and remaining gate

Eight portable automated tests cover round-trip verification, wrong keys/messages, per-byte signature mutation, malformed public points and encodings, zero/negative integers, DER padding, fixed-width padding, rejection of encodable but out-of-range scalars by verification, and harmless default/error CLI paths. Linux adds a ninth test for explicit unsupported-platform failure. Test keys are software-generated by OpenSSL and provide no hardware evidence.

Physical result on 2026-09-20: the debug binary passed on this arm64 Mac running macOS 26.6 (25G72) outside the agent filesystem sandbox. Key creation, unavailable private export, independent fixed-message verification, DER/P1363 round-trip verification and changed-message rejection all completed. No manual codesigning, entitlement changes or permanent key storage were performed. This result is limited to ephemeral use by this binary on this machine, not every Apple model or hosted macOS runner.

The sandboxed attempt first failed at key creation with OS code -26276. Repeating the same binary with approved execution outside the sandbox succeeded. This is an observed environment difference, not a definitive interpretation of that OS code or a reason to silently relax a production sandbox.

P04a does not complete P04. P04b must investigate persistent Data Protection Keychain storage, signed-binary identity and entitlements, retrieval after restart, access isolation, locked-device behavior, denied access and any chosen interactive cancellation policy. The wrapper documents signing/entitlement requirements for DataProtectionKeychain; do not assume ephemeral success proves deployable durable storage. No production fallback is selected if hardware or packaging requirements cannot be met.

## Dependencies and sources

Pinned security-framework 3.7.0 and security-framework-sys 2.17.0 are MIT OR Apache-2.0. The existing OpenSSL 0.10.81 dependency provides independent verification and encoding, with the same native OpenSSL prerequisites as the WebAuthn experiment. No new license exception or advisory ignore is requested. Run `python3 scripts/check.py` and `python3 scripts/dependencies.py` before review.
