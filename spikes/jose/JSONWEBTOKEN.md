# Bounded jsonwebtoken compatibility assessment

Assessment only, not a production library selection. The exact dev dependency is jsonwebtoken 11.1.0 with default features disabled. No built-in crypto backend or PEM feature is enabled; the existing OpenSSL software-key pattern supplies the test signer. No native API, Keychain item or production key is involved.

## Result

The public encoder supports a custom signer and preserves the current deterministic protected-header bytes for the three profile-vector artifacts. It serializes `typ`, `alg`, `kid`, matching the revised [header proposal](../../docs/architecture/deterministic-headers.md). The historical experiment instead required canonical `alg`, `kid`, `typ`; its incompatibility remains covered by negative checks. Both orders are valid JSON/JWS choices, not an upstream cryptographic vulnerability.

The passing negative demonstration checks literal observed header bytes, their inequality with the literal canonical header, exact callback signing input, preserved one-field payload bytes, a raw 64-byte signature, public-key-only verification, and altered-message rejection. A bounded follow-up also parses the existing independently generated `candidate-envelope-vector.json` canonical envelope string and confirms the public encoder preserves those exact nested payload bytes. Its header still differs from the candidate canonical header. This single ASCII/integer fixture is not full JCS conformance or a production schema/parser assessment. In particular, it does not show that encoding an arbitrarily ordered map performs canonicalization.

The current `candidate-profile-vector.json` supplies independent deterministic headers and canonical payload strings for the issuer envelope, agent execution proof and enrollment possession proof. The assessment checks exact emitted header and payload bytes, exact callback signing input, the profile field in each payload, public verification, wrong-key rejection, signature mutation rejection and failure after changing only the profile while retaining the original signature. These are bounded compatibility checks for three fixtures, not a general canonicalization guarantee. Signatures differ from the fixture signatures because the assessment uses a fresh unrelated key; the compared bytes are headers, payloads and signing input.

Verification uses OpenSSL outside the candidate JWT verifier: it is independent of jsonwebtoken serialization, not independent of the OpenSSL cryptographic provider. This does not assess `JwtVerifier` or the production profile gate. The current vectors satisfy the tested exact-header prerequisite; passing them does not mean all required compatibility checks passed. Profile tamper rejection shows signature binding, not policy rejection of a validly signed unknown profile.

An exact test-only opaque handle selects one ephemeral software key. Unknown, empty and suffix-extended handles and ES384 are rejected before signing. This routing policy belongs to the test provider, not the library. The factory receives the algorithm and handle but not the header's `kid`: the test changes `kid` and demonstrates that the same key still signs successfully. Header identity and trusted handle must therefore be bound by the application; this is not automatic library enforcement. The `EncodingKey::from_ec_der` container holds handle bytes only on this path; these bytes are intentionally not DER. No native key routing or key confinement is established. The generated key is unrelated to the fixture's trusted issuer key, so re-signing its payload proves byte compatibility, not fixture issuer authority or evidence validity.

The provider is process-global and cannot be installed twice. One integration-test binary contains one assessment test, so its static state does not affect other integration-test executables. Unused verifier/JWK provider interfaces deliberately remain unsupported and are not production-ready defaults.

## Decision boundary

The historical canonical-header profile remains incompatible. The revised deterministic-header proposal has bounded encoder compatibility evidence, without a custom JOSE assembler, duplicate parser, extra-header workaround or raw-payload workaround. Production parsing, enrollment, trusted key resolution, duplicate rejection and authorization remain outside this assessment. A valid signature alone is not approval or authorization.

This is not library adoption or a P06a freeze. Remaining gates include selecting the production encoder/verifier boundary, proving strict parsing and profile rejection, binding trusted role/type/algorithm/kid/key/handle before signing, and deciding process-global provider initialization and failure behavior. Native key confinement and deployment qualification remain separate gates. The revised header and crypto-profile proposals do not by themselves settle those choices. Adding further libraries or widening the experiment is not an implied next step.
